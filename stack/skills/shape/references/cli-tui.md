# CLI 与 TUI 的交互立项

仅在目标产品实际包含终端入口时使用。CLI 命令和 TUI 视图都从用户任务展开，与 API 草案反复调整。

## CLI：先写完整会话

写出用户完成核心任务会输入什么、看到什么、失败后怎么继续。参考 [API 与 CLI 草案](api-experience.md#示例api-与-cli-草案)，展示命令、输出、退出结果和重试；不要只列待实现的子命令树。

检查任务相关的体验：

- 命令对象、动词、参数和默认值能从任务推断；帮助能让用户发现入口和下一步。
- 简单任务有简短路径；必要上下文只输入一次；避免将底层配置全部映射成必填 flags。
- 成功输出交代结果与产物位置，失败说明原因和可执行的恢复方法。
- 有状态或耗时操作提供适当反馈，并说明中断、重复执行和恢复的行为。
- 同时服务脚本时，明确稳定的结构化输出、stdout/stderr、退出码、管道输入及无 TTY 的行为；交互提问不能让脚本挂起。

把会话与 API 样例对照：命名与状态是否一致，交互有没有弥补 API 不必要的复杂度，API 有没有提供输出所需的数据？从使用体验修改两者，不按内部函数数量生成命令。

先写可评审会话，再用实际终端或最小可运行 CLI 验证最不确定的行为。mock 命令必须标明，不覆盖用户已有的原生命令，也不把尚未实现的草案加入正式帮助。

## TUI：验证操作与状态

先确定用户动作、焦点位置、状态变化和结果反馈，再安排视图。用可运行的最小终端交互验证核心路径，复用项目已有工具；不为立项先搭建完整 TUI 框架。

按具体交互验证：

- 键盘操作可发现，移动、选择、提交、返回与取消语义清楚。
- 焦点始终可辨认；错误后输入和选择得以适当保留；长操作有反馈和可理解的中断结果。
- 在目标最窄与常见终端宽度、resize、无颜色等相关条件下，关键内容和动作仍可达。
- 明确没有 TTY 时使用非交互 CLI、拒绝执行或采取其他已设计的路径。

可以用 HTML 解释 TUI 的视图结构和状态交互；终端的按键、焦点、TTY、重绘与中断仍需在终端验证。浏览器原型或静态字符画不能证明这些行为已经可用。

## 记录证据

保留实际命令或按键、初始条件、关键输出和观察结果。没有终端控制能力时交付可运行入口并标明尚未验证；不要把设计稿的预期输出写成实测输出。
