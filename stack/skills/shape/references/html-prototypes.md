# 原生 HTML 交互原型

在立项阶段，用可运行的前端部件与任务路径确认交互。实现使用原生 HTML、CSS 和 DOM JavaScript，不引入 UI 框架、构建器或组件库；可用单个 HTML 文件，也可拆成少量本地文件。

## 原型范围

从核心用户动作选择需要验证的部件和连接路径，例如输入、选择、预览、提交、反馈与恢复。把这些部件放进真实任务上下文，检查用户能否发现和完成下一步。已有视觉与内容约定应体现在原型中，细节投入以验证问题所需为限。

使用最小 fixture 或明确的 mock 数据。对实际任务涉及的加载、空内容、无效输入、错误和成功状态提供可操作的路径；不必为无关状态造功能。模拟状态应清楚标明，不能假装已连通后端。

原型中的点击和输入要产生对应变化，返回、取消和重试应按设计工作。状态说明应出现在产品上下文中；原型调试用的状态切换入口与正式交互分开呈现。

## 浏览器验证

用现有浏览器控制工具打开实际页面，沿核心任务操作，核对：

- 输入和动作是否容易理解，结果与后续动作是否清楚。
- 原生语义控件、标签、键盘操作与焦点是否支持实际使用。
- 错误出现的位置和文案能否帮助恢复，重试是否保留适当上下文。
- 在目标屏幕宽度和内容长度下，关键操作是否仍然可见、可用。

根据原型需要选择本地文件或轻量静态服务，记录实际打开的地址和复现步骤。没有浏览器控制能力时交付可运行文件并标明交互未验证；截图和 DOM 静态检查不能代替操作结果。

## 反查 API 与交接

把用户动作、组件状态和 API 请求/响应连起来检查。原型新增的步骤、失败信息或进度反馈若缺少 API 支持，回到接口草案调整。接口返回若迫使用户理解内部实现，也需要重新设计交互或 API。

记录交互试用引起的方案变化，以及哪些状态仍为模拟。原型确认后再确定生产框架与实现切片；原型代码可以是验证材料，不要求直接演变成生产架构。用户反馈与代理试用分别记录，实际验证也不代表用户已经接受所有取舍。
