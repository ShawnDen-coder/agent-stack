# 从调用者设计 API

用于库接口、HTTP 路由或供 CLI/界面消费的应用接口。根据实际产品选择适用部分。

## 先写调用，再补结构

用一个代表性任务写出调用者真正会写的代码或请求，展示输入、返回与后续动作。让样例暴露调用顺序、初始化、配置和默认行为；先不要从类型、签名、内部类、数据库表或 SDK 的字段列表生成公共 API。随后草拟类型、签名与模块，检查它们能表达样例的输入、结果和失败；若不能，调整样例与设计直至一致。

检查这些样例能否直接说明：

- 用户能从任务自然推断入口名称、参数和结果含义。
- 必填信息来自用户已知的上下文；默认行为可预测，不要求反复传递同一配置。
- 返回结果足以完成下一步，而不是暴露内部对象让调用者拼装。
- 相关失败能被调用者识别和处理；错误提供有用上下文，CLI 或界面也能解释它。

只处理当前任务实际涉及的状态。异步、取消、重试、分页、批处理或副作用存在时，把它们放进调用样例；没有消费者时不预建这些能力。

## 示例：API 与 CLI 草案

任务是假想的“导出本地报告”，以下输入和输出是设计草案，尚未运行。先从调用者写出成功与可恢复失败：

```typescript
await exportReport({ source: "sales.csv", destination: "sales.pdf" });
// => { ok: true, path: "sales.pdf" }
await exportReport({ source: "missing.csv", destination: "sales.pdf" });
// => { ok: false, code: "SOURCE_NOT_FOUND", source: "missing.csv" }
// 调用者修正 source 后重试同一操作。
```

若产品也有 CLI，用同一任务反查草案：

```text
$ report export missing.csv --out sales.pdf
找不到输入文件 missing.csv；检查路径后重试。    (退出 1)
$ report export sales.csv --out sales.pdf
已导出 sales.pdf                                 (退出 0)
```

最初 API 若要求内部 `reportId`，会迫使 CLI 用户先查 ID；据此改为接受用户已有的文件路径。CLI 又需要指出哪个输入不存在，因此 API 错误携带 `source`，让两边都能给出恢复信息。纯库可以只采用 API 讨论，不必增加 CLI；具体参数、错误与文案仍需按真实任务实验。

## 按入口验证

| 入口               | 需要先看到的使用方式                   | 最小验证方式                                                         |
| ------------------ | -------------------------------------- | -------------------------------------------------------------------- |
| 库                 | 导入、配置、成功返回、失败处理         | 写调用者脚本或契约测试，验证样例是否可用；stub 的行为需标明          |
| HTTP 路由          | 方法、路径、请求、响应和相关错误       | 从实际客户端任务发起请求或运行薄契约实验；文档中的 JSON 不是运行证据 |
| CLI/界面的应用接口 | 用户动作如何转成输入、结果如何成为反馈 | 用真实交互或明确的 stub 走完任务，记录接口缺失与界面补救步骤         |

草案可先通过可运行 mock 或小范围实现验证；不必为了验证一个接口搭建完整服务。mock 只证明调用与状态约定，真实权限、持久化和外部行为留在明确的实施验收中。

## 与交互一起修改

从 CLI 或界面反查 API：用户是否被迫提供内部 ID、猜执行顺序、理解底层参数，或在一个简单任务中反复查询和拼装数据？确定这些负担属于必要业务信息，还是可以由更好的 API、默认值或交互承担。

反过来用 API 状态检查交互：界面给出的成功、失败、进度、取消和下一步，是否有对应契约支持？若原型只模拟了结果，明确记录尚缺的接口。保持用户术语与状态含义一致，不要求 HTTP 路由、库函数、CLI 命令机械采用同一种语法。

方案影响已有接口时，说明真实调用者与兼容成本。以可观察的用户体验和必要约束作取舍依据，不把框架便利或少写几行内部代码作为唯一理由。
