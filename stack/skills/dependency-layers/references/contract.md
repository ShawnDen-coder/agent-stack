# L0–L3 依赖规范

本规范约束代码模块的静态依赖，适用于不同语言和项目；工具的默认规则不代替本规范。

## 层级与模块归属

| 层级 | 职责                           | 典型内容                                       |
| ---- | ------------------------------ | ---------------------------------------------- |
| L0   | 项目外部提供的依赖             | Runtime、标准库、第三方库、SDK、外部工具       |
| L1   | 基础契约、纯规则与单项能力适配 | Schema、值对象、纯函数、文件或外部服务 adapter |
| L2   | 用例与能力组合                 | 组合基础模块完成一类任务的方法                 |
| L3   | 应用入口与场景编排             | 入口、场景选择、应用级工作流                   |

目标项目必须列出生产源码范围、模块归属、公共入口和 L0 访问范围。一个内部模块只能属于 L1–L3 中的一层；模块可为一个 package、目录或文件。层级根据职责确定，不要求目录叫 `l1`、`l2`、`l3`，也不要求每个小项目凑齐三层。

合法依赖方向不等于每一层都值得存在。按知识和状态所有权划分模块，而非机械按 load、validate、save 等执行阶段切分；评审状态是否有单一所有者、公共 API 是否隐藏内部表示。每个保留的边界应承担真实职责，例如隐藏策略、适配或复杂度，不为重复同一接口制造空转发；有独立职责的 adapter 仍有价值。

对可确定的约束，优先利用语言原生类型、可见性、导出边界和 lint；仍需判断的约束用简短说明或失败示例表达，并按项目实际验证。上述职责判断借鉴并改写 [pstack 的阅读负担原则](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-minimize-reader-load/SKILL.md)与[结构化约束原则](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-encode-lessons-in-structure/SKILL.md)，不引入其完整流程。

## 依赖契约

### DL-01：方向与跨度

内部模块默认只直接依赖相邻低层。存在完整间接链路是正常行为；跨度检查针对每条直接依赖边。

| 依赖                | 默认结果                                           |
| ------------------- | -------------------------------------------------- |
| L3 → L2、L2 → L1    | 允许，经目标模块公共入口访问                       |
| L3 → L1             | 禁止；可按 DL-04 精确放行，最多跳过一层            |
| 任意内部低层 → 高层 | 禁止，包括通过未归层 helper 的间接反向依赖         |
| 同层不同模块        | 允许经公共入口单向复用；独立模块可另行禁止互相依赖 |
| 同一模块内部        | 允许内部引用，仍须满足无环等项目约定               |

不得为了经过中间层添加空转发，也不得仅为消除违规而修改模块层级。合法的简短路径应明确登记例外，或在确认职责发生变化后调整模块归属。依赖指代码引用；依赖注入中下层调用传入的回调，不等于下层静态依赖上层实现。

### DL-02：L0 按用途约束

L0 与内部层分别处理：

- 外部系统能力，如文件、网络、数据库和子进程，默认由 L1 adapter 访问。L2 直接访问须登记具体模块与目标 API 的例外；L3 不得直接操作这些外部系统。
- 通用库、标准库纯函数及框架入口 API，按目标模块职责设置允许列表。例如 数据契约使用校验库、应用入口使用框架 API。此类依赖不受内部层跨度公式约束，仍须遵守纯业务模块不做 I/O 等规则。
- L1 也不能任意使用未声明的外部包。依赖清单、生产/开发用途和层级访问范围都要核对。

因此，约束 L0 不能靠统一禁止所有第三方导入实现，也不能通过允许所有外部包规避。

### DL-03：公共入口与无环

跨模块只引用已声明的公共入口，内部文件由所属模块自行使用。公共入口的类型与重导出同样受检查；重导出链的每条边都要合法，不能通过 barrel、`__init__` 或 helper 掩盖反向和越层引用。

合法的公共入口可以汇集本模块 API。循环检查同时考虑源码文件和模块聚合后的依赖，避免文件无环但模块之间成环。检查器应区分语言的结构性声明与业务依赖，避免机械地误报循环。

### DL-04：例外是具体的边

每条例外记录源模块或文件、目标公共入口、理由及仍须保留的约束。内部跨层最多跳过一层；例外不能放行反向依赖、循环或目标内部实现。

例外应进入检查配置，与普通规则一起审查。不要放宽整个目录或整层，也不要用全局 ignore、关闭类型检查或降低错误等级代替。失效或未使用的例外需要提示并清理。

### DL-05：检查范围必须可见

- 覆盖声明范围内的全部生产模块，包括没有导入的孤立模块；缺少归属、重复归属、规则匹配为空及解析/解析路径失败均须报告。
- 类型引用也算依赖。别名、静态可解析的动态导入和重导出必须用目标语言检查器解析，不用字符串搜索代替依赖图。
- 测试、构建脚本和生成代码声明独立范围与访问规则，不能笼统忽略后声称全仓库符合规范。生产代码不得反向引用测试代码。
- 无法静态解析的插件加载、反射、宏展开或运行时外部工具调用，需要另列运行验证。报告明确指出检查器未覆盖的语法、target 或 feature。

## 验收案例

目标项目用最小临时 fixture 验证配置，至少覆盖下表。负例必须因预期依赖边违规而失败；配置损坏、依赖未安装或模块路径写错不算拦截成功。

| ID  | 案例                                    | 预期                       |
| --- | --------------------------------------- | -------------------------- |
| C01 | L3 → L2 公共入口 → L1 公共入口          | 通过                       |
| C02 | L3 直接引用 L1 公共入口，未登记例外     | 失败                       |
| C03 | C02 对具体源、目标登记例外              | 通过；换目标或换源仍失败   |
| C04 | 相邻高层直接引用低层内部文件            | 失败                       |
| C05 | 低层直接或经 helper 引用高层            | 失败                       |
| C06 | 同层文件循环、聚合模块循环              | 失败                       |
| C07 | 仅通过类型引用造成 C02 或 C05           | 失败                       |
| C08 | 借重导出或别名造成 C02、C04 或 C05      | 失败；合法相邻重导出仍通过 |
| C09 | 新增未归层的生产模块，包括孤立模块      | 失败                       |
| C10 | 声明模块不存在、空扫描或检查器错误      | 失败，并区分于依赖违规     |
| C11 | L1 访问允许的 L0 SDK；L3 直接访问该 SDK | 前者通过，后者失败         |
| C12 | 指定模块使用职责允许的通用 L0 库        | 通过；其他模块不自动获准   |

测试输入可以不同，规则含义与预期必须一致。尚未执行的案例和工具覆盖缺口单独记录，不把文档、配置格式或类型检查成功描述为架构验证通过。

## 接入与交付

先确定目标项目模块表，再接入其原生工具配置与 CI。依赖版本使用目标项目的包管理器和锁文件；复用现有 lint、format 与检查入口。先观察并修复既有违规，不静默将全部旧违规列为豁免。

交付应包含模块表、允许矩阵、公共入口、例外、检查命令和正反例结果。检查失败返回非零；CI 不允许架构任务失败后继续当成成功。
