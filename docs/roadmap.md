# 后续实施顺序

先完成一条可以验证的使用路径，再扩充工具或命令。文件结构按部件、组合与集成演进，工具的实际安装能力逐项实现。

## 当前基础

- 单包 npm CLI、严格类型、构建、lint 和真实 CLI 测试。
- 六个工具、两个集成和两份 profile 的声明。
- `validate` 检查格式、引用、平台和能力要求。
- 跨系统 CI 定义。

## 下一步：只读环境检测

实现一个真实的 `doctor` 增量：先检查 Node/npm、Git、pnpm、uv、Pi 的路径与版本，区分未安装、版本不符和 PATH 问题；随后增加 herdr、Otty、Rex 的原生检查及集成状态。

检测报告同时保留仓库要求与本机观察，不能因文件存在就宣称能力可用。App 未运行、平台不适用与未安装分别显示；默认不刷新认证或发起收费模型请求。

## 版本解析与锁定

实现 profile 选择器的解析，生成真实 `stack.lock.json`，记录各目标平台的确切版本、来源和可验证发行物。随后支持严格按锁安装、缺少目标时失败、安装来源识别与结构化计划。

先用 Pi/pnpm 的 npm 来源和 uv 官方发行物验证闭环，再扩展其他渠道。保留原生包管理器对传递依赖的锁定能力。

## 配置与集成应用

从一个 Pi 原生配置文件和一个 skill 开始，定义源文件、本地覆盖、管理范围、预览、备份、原子写入及重复执行行为。再接入 Pi/herdr 原生集成。

用干净目录和已有配置目录验证，认证和会话留在各自工具中。首次引导以后由这些已经验证的小操作组合而成。

## 更新与替换

升级单个部件，生成候选锁文件，检查最小依赖变化并验证组合后再提交。恢复配置与回退程序分别说明能力和限制。

使用独立 Rex profile 做替换实验：保留通用流程，重新检查平台、控制 skill、状态能力和运行中的会话；新组合通过之前保留旧环境。

## 从真实任务沉淀工作流

编写并验证 `shape`、`implement`、`verify`。通用判断留在 skill，确定性操作落到脚本或检查，项目知识留在业务仓库。再在另一台机器复现同一组合并完成真实任务。
