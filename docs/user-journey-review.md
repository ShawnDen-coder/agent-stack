# Agent Stack 用户旅程审查

基线：`94e8d589d42578a480a664eee61d15d5d9c1374d`；本次为现状分析和可验收的后续建议，不代表建议功能已经实现。使用对象是需要在多台设备上维护个人 coding 环境、在业务仓库工作并沉淀可复用 skills 的使用者。证据来自此基线的源码、文档和本机只读命令；没有读取模型凭证、操作真实用户目录、安装工具或验证模型调用。产品目标已通过 Nowledge Mem MCP 定向检索核对，检索依据见文末。

## 当前使用路径与成功条件

1. **获取 CLI 与配置。** 当前没有正式发布，包为 `UNLICENSED`；按照 [README](../README.md#从源码试用) 获取源码 checkout，准备 Node 24+、npm、Git 和 pnpm 12.15.0，安装 CLI 依赖并 build。CLI 包和配置仓库是不同职责，即使未来安装包或 SEA 可用，运行时仍需要 Git checkout；见 [架构：配置与状态归属](architecture.md#配置与状态归属)。不要把同名公开 npm 包视为本项目的已发布版本。
2. **新机准备与锁。** 在原生 macOS arm64/x64，检查 Node、npm、Git，准备网络，将 `~/.agent-stack/bin` 放在当前 shell PATH 最前。已有团队或个人审阅过的共享锁则复用；没有时按 [Quickstart](quickstart.md#macos-的完整-coding) 选择本机目标创建锁、校验、预览，再交互确认 setup。首次受管 Pi 安装要求 npm 11.12.1；默认锁存在时，即使提供其他 `--out` 也会被拒绝（[lock.ts:61](../src/commands/lock.ts#L61)）；不能将 `--out` 当成绕过方法。需多设备共享时，在首次创建时明确选择所有需要的受支持目标，再以 Git 同步经审查的锁。锁是资产预期，不是跨设备固定的 npm 传递依赖闭包。
3. **观察已有工具。** 完整 coding 当前要求受管 Pi/pnpm；已有外部入口会阻塞而不会被接管。uv/Herdr 在匹配条件下可外部复用。setup 需要完整版本、目标资产、PATH 与资源计划均满足，最终隔离 Pi TUI 和 Herdr 状态验证成功后才绑定；凭证和会话仍由原生工具管理。Windows x64 仅支持 Herdr-only，Linux/WSL 完整 coding 不支持；见 [Quickstart](quickstart.md#macos--windows-x64-的-herdr-only-setup)。
4. **启动与日常任务。** 在同一 PATH 环境启动本机 Herdr，进入本机活动 pane；再用绑定的 checkout 运行 `run coding`。从源码使用时，先在业务项目保存其绝对路径，再回到配置 checkout 调用 `pnpm cli run --repo . coding --cwd "$PROJECT_DIR"`；`pnpm cli` 是配置仓库的 npm script，`--cwd` 才是 Pi 的业务工作目录。当前 `validate`/`lock` 不读取 `AGENT_STACK_REPO`，而 setup、doctor、run 会读取，因此从业务目录操作时所有命令均显式传配置 checkout 的 `--repo`（[validate.ts:29](../src/commands/validate.ts#L29)、[lock.ts:61](../src/commands/lock.ts#L61)、[setup.ts:115](../src/commands/setup.ts#L115)）。使用实际仓库路径和项目路径替换变量；不要把业务目录误作 `--repo`。先用 `--dry-run --json` 检查绑定和当前 pane，再启动。Pi 的原生参数放在 `--` 后，非 TUI 或绕过必需资源的参数会被拒绝；实际模型登录、授权和使用属于 Pi 原生流程，不包含在 setup 的验证中。
5. **工作方法。** coding Agent 将 shape、implement、verify 作为按需工作流：界定目标和验收、实施、通过真实入口验证；具体文件见 [coding Agent](../stack/agents/coding.md)。在业务仓库按其规则交付，通用方法经审查后可编辑配置 checkout 中的 skills 并通过 Git 同步；不要把项目特定规则、认证或会话混入共享配置。当前没有独立的 skill 沉淀向导。
6. **Git 更新与迁移。** 在稳定路径更新 checkout 后，先阅读 diff、执行 validate/lock 校验和 setup dry-run；已纳入签名的原生配置、coding Agent 和三个 `SKILL.md` 变化时，按资源计划处理并重新 setup/doctor；引用支持文件目前未完整纳入签名，见后文的隔离复现。CLI 源码或 CLI 依赖变化时，源码入口需要按锁重新安装依赖并 build。components、profile 或 integrations 声明语义变化可能使旧锁的声明摘要失效，当前没有 lock update，不应靠删除锁或 journal 强行继续（[validate-lock.ts:44](../src/core/validate-lock.ts#L44)）。资源仍引用 checkout，移动或另建 checkout 后不能假定旧绑定自动迁移：现有上下文选择、锁路径及资源校验见 [coding-context.ts](../src/adapters/coding-context.ts#L24) 和 [coding-readiness.ts](../src/adapters/coding-readiness.ts#L41)。成功绑定其他 profile 会替换唯一的 defaultBinding；返回 coding 时，指定原配置 checkout、profile 和适用锁重新预览并运行 coding setup，通过后再 doctor/run，不能假定旧 proof 仍绑定（[coding-readiness.ts:181](../src/adapters/coding-readiness.ts#L181)）。新机器应重新执行本机 setup，不复制 `.agent-stack` 设备状态或工具认证来冒充安装。
7. **中断、重试与独立升级。** 失败后保留原生工具、配置和设备回执，先查看 dry-run/doctor，再按提示重跑 setup；资源 journal 的部分恢复可能要求再次运行以复核新计划（[setup-coding.ts](../src/commands/setup-coding.ts#L477)）。遇到目标或备份被改变时会阻塞人工处理，不能建议删除 journal 强行继续（[coding-resource-transaction.ts](../src/adapters/coding-resource-transaction.ts#L163)）。目前锁更新、单部件升级与程序回退尚未实现（[roadmap](roadmap.md#待完成)）；第三方工具可独立于 CLI 发布，但本 CLI 不提供完整的安全升级流程。

## 已复现的第一印象

在基线构建后的真实 CLI、临时空 `HOME` 和不含用户工具的 PATH 下：

- `validate --repo . --json` 返回 `valid: true`、6 components / 2 integrations / 2 profiles。这只证明声明有效。
- checkout 没有默认共享锁时，`setup --repo . --profile coding --dry-run --json` 返回 `{"error":"Cannot read lock file"}`；文件打开失败没有区分缺失、权限等原因，也没有指出所选锁路径及首次创建锁的下一步。损坏 JSON 已有独立的 `Lock is not valid JSON` 错误，改进时应保留该分流。
- 未绑定时，`run --repo . coding --dry-run --json` 返回 `No completed coding setup; run agent-stack setup --profile coding`，不会启动 Pi。该结果尚未进入 Herdr pane 检查。提示中的命令省略了 `--repo`：在业务项目目录复制时可能选到错误的配置源。
- `run --help` 显示 `--repo`、`--cwd`、`--dry-run` 和 `--` 后的 Pi 参数；文档中的源码 `pnpm cli` 必须从含该 script 的 checkout 执行。

根会话在同一基线、独立临时空 HOME 与 `PATH=/usr/bin:/bin` 复现了相同的 setup/run 结果，并确认 `doctor --repo <config-repo> --profile coding --json` 给出 `ready: false`。这里的路径均为占位符。

Coco 在同基线独立复现：同版本外部 pnpm 使 setup 退出 1，但计划动作仍显示 `verify reuse; ownership unknown`。源码中通用动作只按观察状态生成（[setup-plan.ts:134](../src/core/setup-plan.ts#L134)），coding 的 mode 与 blocker 另行计算（[setup-coding.ts:285](../src/commands/setup-coding.ts#L285)、[setup-coding.ts:345](../src/commands/setup-coding.ts#L345)），两者会误导用户。

Coco 在一台已验收受控安装上观察到 doctor 为 16.45 秒、非 Herdr pane 的 run dry-run 为 15.91 秒，后者才提示缺 pane；这是单机样本，不是性能 SLO。源码先计算 coding readiness，再检查 Herdr context（[run.ts:29](../src/commands/run.ts#L29)）。后续可评估安全的廉价前置提示和进度反馈，不能因此跳过整树及最终复核。

Coco 的隔离 coding 资源 fixture 删除整个 `shape/references/` 后，`inspectCodingResources` 仍 ready 且 signature 不变。源码的资源清单只列三个 `SKILL.md`（[coding-resources.ts:164](../src/adapters/coding-resources.ts#L164)），但 shape 文档引用了这些支持文件（[shape/SKILL.md:20](../stack/skills/shape/SKILL.md#L20)）。此实验没有在删除后复测完整 TUI 或 doctor，不推断二者结果。

上述只读 CLI 复现、单机计时和隔离资源 fixture 分别有各自范围；它们不构成首次在线锁解析、真实安装或模型验收。

## 建议实施顺序

先做缺锁诊断和双路径 Quickstart，并复现 pnpm bootstrap 冲突；随后处理 checkout 迁移、唯一绑定切换和安全候选锁；外部入口复用单独作为高成本设计与测试。再做可恢复诊断和受审阅的锁更新/独立升级。每个切片以临时 HOME、真实 CLI 和适用平台原生证据验收；保持 Windows Herdr-only、能力要求和原生工具所有权。发布、真实认证或模型调用另行授权和单独验收。
